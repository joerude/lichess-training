### 1. Resolved: teaching handoff directed learners to the wrong completion-handler file

**Locations:** `docs/learning/first-working-addon.md:37`, `lessons/0002-persisted-training.html:26`, `reference/0002-message-and-storage.html:13`.

**Trigger and impact:** Following the explicit exercise to find the completion button handler in `extension/ui/dashboard.js` does not find that handler or `training.setCompletion`. The actual shared handler is in `extension/ui/page.js:73`. Both the lesson and reference repeat the older responsibility assignment, making a central code-tracing exercise unnecessarily confusing for a beginner.

**Fix:** Point the exercise and responsibility table to `ui/page.js`, explain that popup/dashboard mount this shared page behavior, and show the actual flow through `ui/client.js` and `background-transport.js` (wired by `background.js`) to the service and repository. This is a documentation correction; new product tests are unnecessary.

**Resolution at `2165038`:** All three teaching documents now identify `ui/page.js` as the shared completion handler. They describe the client and transport wiring, distinguish dashboard-specific responsibilities, and direct the code-tracing exercise to the implemented file. Verified against the current source.

### 2. Resolved: successful automatic refresh left a recovered load error visible

**Location:** `extension/ui/page.js:56` (successful render), in combination with `extension/ui/page.js:84` (resume refresh).

**Trigger and impact:** A snapshot request fails transiently and `showError` displays the storage/background error. The user switches away and returns; a later focus/visibility refresh succeeds and renders the journal, but the previous red error still instructs them to refresh or check storage. Only the explicit Refresh click or a later successful mutation clears it. Data remains correct, but the error state contradicts a recovered load.

**Fix:** Clear an outstanding load/refresh error when a later snapshot refresh succeeds. Keep restore/export failures scoped appropriately so an unrelated automatic refresh does not silently erase an actionable failure. A focused recovery-state check is sufficient.

**Resolution at `2165038`:** `createTrainingController` passes the failed command type to `showError`; `mountTrainingPage` forwards it to `createPageFeedback`. Rendering a persisted snapshot invokes `recoveredSnapshot`, which clears only a preceding `training.getSnapshot` error. Restore/completion errors retain their command source, while direct export/file errors use the external default and survive unrelated refreshes. The new feedback regressions cover recovery, preservation of actionable errors and saved-success replacement; the existing controller failure test also checks command-source forwarding. Source wiring and regression behavior satisfy the original finding.
